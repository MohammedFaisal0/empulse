# EMPULSE data schema

Generated by `ml/02_build_dataset.py` from the real CSV files in `data/generated/` (do not edit by hand; re-run the script).

All data is **synthetic**. As-of week: **2026-10-05**. 1,240 people, 6 departments, 31 teams, 52 weekly points per person.
Booleans are 0/1. Dates are ISO `YYYY-MM-DD`. Empty cell = null. Primary keys are called `id` (except `employee_current.employee_id`).

## Relationships

```
departments 1-n teams 1-n employees
employees.manager_id -> employees.id      (line manager; ~5-12 direct reports)
employee_current / weekly_metrics / skills / ideas / interventions -> employees
recognitions.giver_id / receiver_id -> employees
economic_impact_monthly -> departments
```

## Model files (`ml/models/`)

`burnout_model.pkl` and `attrition_model.pkl` are joblib bundles. Load with `ml/empulse_ml.py` (`load_bundle`, `predict_proba`, `drivers`, `simulate`). Do not retrain in web requests. `simulate()` powers the What-if Simulator (H13). Scores in `employee_current` were produced by these models.

## Rules the API must enforce (from the design)

1. **No leaderboards.** Never order people by `performance_score`, `innovation_score` or recognition counts. Lists are alphabetical (`full_name`).
2. **Wellbeing is never part of performance.** `performance_score` has no wellbeing input. Show `wellbeing_score` and risk separately.
3. **Privacy by role.** Employee: own rows only. Manager: rows of people whose `manager_id` is the manager (direct reports). HR: any individual, but each profile read must write an `AuditLog` row. Executive: aggregates only.
4. **Small groups are suppressed.** Any aggregate over fewer than 5 people returns "suppressed", never numbers.
5. **Sensitive fields:** `monthly_income_sar`, `income_ratio`, `attrition_*`, `burnout_drivers` are HR/manager-only (manager: direct reports only). Employees see their own wellbeing and their own risk explanation, never someone else's.
6. **Human in the loop.** An intervention only starts when `human_approved = 1`.
7. Burnout and attrition risk are **decision support, not a medical or psychological diagnosis**.

## Tables

### `departments` (6 rows)

The 6 departments of Horizon Group.

| Column | Type | Description |
|---|---|---|
| `id` | int | Primary key. |
| `name` | text | Department name. |
| `head_id` | int | FK -> employees.id, the department head. |
| `headcount` | int | People in the department (derived; recompute in the app). |

### `teams` (31 rows)

The 31 teams. A team has several line managers (each with 5-12 direct reports).

| Column | Type | Description |
|---|---|---|

### `employees` (1,240 rows)

Static profile of each person (1,240). One row per person.

| Column | Type | Description |
|---|---|---|
| `id` | int | Primary key. |
| `employee_code` | text | Display code, HZ0001... |
| `first_name` | text | First name. |
| `last_name` | text | Last name. |
| `full_name` | text | First + last name. Unique. |
| `email` | text | Work email. Unique. The 3 demo accounts use layla@, yasmin@, rana@horizon.demo. |
| `gender` | text | M or F (used only for fairness analytics). |
| `age` | int | Years. |
| `job_title` | text | Job title. |
| `job_level` | int | 1-5 (5 = department head). |
| `department_id` | int | FK -> departments.id. |
| `team_id` | float | FK -> teams.id. Null for department heads. |
| `hire_date` | text | ISO date. |
| `tenure_years` | float | Years at the company. |
| `monthly_income_sar` | int | Synthetic monthly salary in SAR. Sensitive: HR only. |
| `income_ratio` | float | Salary divided by the median for the job level (model input). |
| `years_since_promotion` | float | Years since last promotion (model input). |
| `work_location` | text | City. |
| `work_mode` | text | Hybrid / On-site / Remote. |
| `app_role` | text | Suggested app role: employee, manager, hr. Users are created only for the demo accounts. |
| `is_manager` | int | 1 if the person manages others. |

### `employee_current` (1,240 rows)

Latest weekly snapshot per person: raw signals, scores and model outputs. One row per person, re-written by the scoring job (in the app: a table refreshed by a management command).

| Column | Type | Description |
|---|---|---|
| `employee_id` | int | PK and FK -> employees.id. |
| `as_of` | text | Week start (Monday) of the snapshot. |
| `workload_index` | float | 0-100 workload pressure. |
| `overtime_hours_monthly` | float | Overtime hours per month. |
| `work_life_balance` | float | 1-4 rolling survey average. |
| `job_satisfaction` | float | 1-4 rolling survey average. |
| `mood_score` | float | 1-5 weekly pulse mood (not a clinical measure). |
| `engagement_score` | float | 0-100. |
| `absence_days_annual` | float | Absence days in the last 12 months. |
| `recognition_90d` | int | Recognitions received in the last 90 days (equals count in recognitions). |
| `training_times_last_year` | int | Training events in the last year. |
| `ideas_submitted_12m` | int | Ideas submitted in 12 months (equals count in ideas). |
| `ideas_approved_12m` | int | Ideas approved or implemented. |
| `ideas_implemented_12m` | int | Ideas implemented. |
| `innovation_score` | float | 0-100 from idea volume, quality, approval and implementation. |
| `task_completion_rate` | float | 0-100 on-time completion. |
| `task_quality_score` | float | 0-100. |
| `collaboration_score` | float | 0-100. |
| `performance_score` | int | 0-100 = 0.30 completion + 0.30 quality + 0.20 collaboration + 0.20 innovation. NEVER includes wellbeing. |
| `performance_tier` | text | Gold >= 90, Silver 80-89, Bronze 70-79, Growth < 70. |
| `wellbeing_score` | int | 0-100 composite of mood, work-life balance, workload, engagement, overtime. Shown separately from performance. |
| `burnout_risk_pct` | int | Model output 0-100 (probability of a burnout event in 90 days). Decision support, NOT a diagnosis. |
| `burnout_level` | text | Low < 40, Moderate 40-59, High >= 60. |
| `attrition_risk_pct` | int | Model output 0-100 (leaving within 12 months). |
| `attrition_level` | text | Same bands as burnout_level. |
| `burnout_drivers` | text | JSON text: {increasing:[{feature,label,value,baseline_value,impact_pts}], protective:[...]} (exact Shapley values vs. the average employee). |
| `attrition_drivers` | text | Same JSON structure for the attrition model. |
| `burnout_change_6w_pts` | int | Burnout risk now minus 6 weeks ago, in percentage points. |

### `economic_impact_monthly` (78 rows)

Economic impact by department and month, derived from risk, performance, interventions and ideas.

| Column | Type | Description |
|---|---|---|
| `month` | text | First day of the month. (month, department_id) is unique. |
| `department_id` | int | FK -> departments.id. |
| `headcount` | int | People in the department. |
| `avg_burnout_risk_pct` | float | Mean weekly burnout risk in the month. |
| `avg_wellbeing_score` | float | Mean wellbeing. |
| `avg_performance_score` | float | Mean performance. |
| `interventions_completed` | int | Interventions created that month that are completed. |
| `ideas_implemented` | int | Ideas implemented that month. |
| `expected_exits_baseline` | float | headcount x 13% / 12 (assumed yearly attrition 13%). |
| `exits_avoided` | float | baseline exits x min(3 x relative risk drop vs first 3 months, 0.5). |
| `retention_savings_sar` | float | exits_avoided x average annual salary x 1.0 (replacement cost multiplier). |
| `productivity_gain_sar` | float | Less burnout = fewer lost productive days: headcount x avg monthly salary x 0.5 x (drop in average burnout risk, in points, vs first 3 months) / 100. |
| `innovation_value_sar` | float | Sum of realized_value_sar of ideas implemented in the month. |
| `program_cost_sar` | float | Intervention costs + platform running cost share. |
| `net_impact_sar` | float | retention + productivity + innovation - program cost. |
| `roi_pct` | float | net impact / program cost x 100. |
